# Pearl: A Beads Web UI

[![CI](https://github.com/htxryan/pearl/actions/workflows/ci.yml/badge.svg)](https://github.com/htxryan/pearl/actions/workflows/ci.yml)
[![Website](https://img.shields.io/badge/website-getpearl.dev-blue)](https://getpearl.dev)

Rich web UI for the [Beads](https://github.com/mantoni/beads) AI work management system.

## Fork notice

This is a **fork of [htxryan/pearl](https://github.com/htxryan/pearl)** (based on upstream
`pearl-bdui@0.12.3`, the last upstream release). Upstream Pearl was built against an older
Beads schema and breaks against **[Beads](https://github.com/gastownhall/beads) `1.1.0`**.
This fork patches those incompatibilities so Pearl works with Beads 1.1.0:

1. **`dependencies.depends_on_id` → `depends_on_issue_id`** — Beads 1.1.0 renamed the
   dependency target column (split into `depends_on_issue_id` / `depends_on_wisp_id` /
   `depends_on_external`). Pearl's SQL still selected/inserted `depends_on_id`, so
   `/api/dependencies` plus issue-detail and filter queries returned HTTP 500 and froze
   the web UI. The SQL now references `depends_on_issue_id` (SELECTs alias it back to
   `depends_on_id`, so the API response shape and the frontend stay unchanged).

2. **Application-generated `id` for `events` / `comments` / `dependencies` inserts** — in
   Beads 1.1.0 the `id` primary key of these tables is a `char(36)` UUID generated by the
   `bd` client, with no database default. Pearl's SQL write path inserted rows without an
   `id`, so every UI write (create, status/priority update, close, comment, add/remove
   dependency) failed with *"Field 'id' doesn't have a default value"* (HTTP 500). The
   write path now supplies `randomUUID()` as the `id`.

Both fixes live in `packages/pearl-bdui/src/{routes,write-service}`; see branch
`fix/beads-1.1-dependencies-schema`.

## Hierarchical relationships in the List view

The List view renders Beads parent/child relationships as a collapsible tree. Relationships
stored as `contains` dependencies work for every issue type and can be nested to any depth.

- Child rows are indented beneath their parent while remaining in the normal issue table.
- Every parent has an expand/collapse control that hides or reveals its complete subtree.
- **Top-level only** filters the table to root issues.
- Sorting is applied within each sibling group, so children stay attached to their parent.
- Parent rows show the completion progress of their direct children.

CLI `parent-child` dependencies are normalized to the UI's `contains` representation when
Pearl starts, allowing relationships created with `bd` to appear in the tree automatically.

## Quick Start

Run Pearl in any project directory that has a `.beads/` folder:

```bash
npx pearl-bdui
```

This starts the Pearl server and opens your browser to the UI.

### Options

```
pearl-bdui [options]

  -h, --help     Show help
  -v, --version  Show version
  --no-open      Don't open browser automatically
```

### Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `PORT` | `3456` | Server port |
| `DOLT_HOST` | `127.0.0.1` | Dolt SQL server host (server mode) |
| `DOLT_PORT` | `3307` | Dolt SQL server port |

## Install

### Via npx (recommended)

```bash
npx pearl-bdui
```

Always runs the latest version. No install needed.

### Global install

```bash
npm install -g pearl-bdui
pearl-bdui
```

### Requirements

- Node.js >= 22
- [Dolt](https://docs.dolthub.com/introduction/installation) (Pearl manages a `dolt sql-server` or connects to your own)
- A project with a `.beads/` directory (created by the `bd` CLI)

### Database Mode

Pearl runs against a Dolt SQL server. On first start, if your project uses the legacy embedded mode, Pearl shows a migration modal with two options:

- **Pearl-managed**: Pearl starts and supervises a `dolt sql-server` for you. One click.
- **External**: Run `dolt sql-server` yourself and provide the host/port.

## Development

```bash
git clone https://github.com/htxryan/pearl.git
cd pearl
pnpm install
pnpm dev
```

This starts the backend (Fastify on port 3456) and frontend (Vite on port 5173) in development mode.

### Project Structure

```
packages/
  pearl-bdui/ # Publishable package: Fastify server + bundled frontend
  frontend/   # React 19 SPA with Vite, TailwindCSS, React Flow
  shared/     # Shared TypeScript types (API contract)
```

### Scripts

| Command | Description |
|---------|-------------|
| `pnpm dev` | Start development server |
| `pnpm build` | Build all packages |
| `pnpm test` | Run all tests |
| `pnpm typecheck` | TypeScript type checking |
| `pnpm test:e2e` | Run Playwright end-to-end tests |
| `task publish` | Build and publish to npm |
| `task publish:dry` | Dry-run publish |

### Publishing

Releases are automated via [release-please](https://github.com/googleapis/release-please):

1. Merge PRs to `main` using [conventional commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, etc.)
2. Release-please opens a release PR with the version bump and generated changelog
3. Merge the release PR — this creates a GitHub release and publishes to npm via OIDC (no tokens needed)

**Manual publish** (for local testing):

```bash
task publish       # build + publish to npm
task publish:dry   # dry-run (no upload)
```
